# Android: автономная выдача WireGuard-туннеля через портал-логин

## Область — три кодовые базы, не одна

Эта фича трогает три независимых репозитория/хоста:

| Что | Где | Git |
|---|---|---|
| Портал (self-service бэкенд) | `/home/lev/vkturn-ios-portal`, задеплоен на `vps` (89.124.71.77) | нет репозитория, деплой напрямую |
| Панель (админ-инструмент) | `/home/vkturn/vkturn-panel/panel.js` на `ai-lan` | нет репозитория, деплой напрямую |
| Android-приложение | `turn-proxy-android` (этот репозиторий) | есть |

Спека лежит в `turn-proxy-android`, т.к. это единственный из трёх с git-историей
и уже существующей практикой `docs/superpowers/specs/`, но описывает все три
стороны.

## Проблема

`PortalLoginDialog`/`PortalApiClient` (коммит `7a0720b`, 2026-08-24) уже дают
Android self-service вход по паролю на портале (`lft.levnas.ru`) — но
`GET /api/v1/config?device=android` намеренно не возвращает ничего про
WireGuard (см. `PortalApiClient.kt`'s комментарий и портальный doc-comment у
`User.AndroidAccounts`: "Android's WireGuard full-tunnel peer is provisioned
by panel.js's existing path... not by this API"). Реально WG-пир для Android
до сих пор заводит АДМИН через `panel.js` вручную (см. `androidlogin`
device-type, добавленный в этой же рабочей сессии 2026-08-29) — родне отдаётся
памятка с логином/паролем ПЛЮС отдельный WireGuard `.conf`, который нужно
вручную вставить в `WireGuardConfigCard`. Это и есть тот самый "донастроить
руками", от которого просит избавиться пользователь: «Android клиент
полностью автономен, не заставлять пользователя что-то до конца настраивать
как например wireguard, всё должно с сервера тянуться как конфиг/подписка».

Готовый прецедент такой автономности уже есть в портале — `handleGenerate()`
(`main.go:574`) для iOS: по кнопке "Сгенерировать конфиг (8ч)" портал сам
генерит WG keypair (`wgGenKeypair`, локальный `wg genkey`/`wg pubkey` — SSH не
нужен, портал живёт на том же хосте, что и интерфейс `wgcl`), сам регистрирует
пир живьём (`swapPeer` → `wg set` + запись в `wgcl.conf`) и отдаёт приватный
ключ клиенту одним файлом. Для Android нужен ровно такой же фокус, но без
ручной кнопки и без 8-часовой ротации (см. "Жизненный цикл пира" ниже —
решение пользователя).

## Решение — общая картина

1. **Портал генерит и хранит перманентный WG-пир для android-логина сам**,
   при первом обращении к `/api/v1/config?device=android` — без участия
   администратора и без ручной кнопки на стороне пользователя.
2. Эндпоинт добавляет в JSON-ответ готовую строку `.conf` (`wgConfig`).
3. **Android просто подставляет её** в уже существующие поля `ClientConfig`
   (`tunnelTransport`/`wireGuardConfig`) при входе по паролю — ноль новых
   экранов, ноль ручной вставки.
4. `panel.js`'s `androidlogin` device-type перестаёт заниматься WG вообще —
   его WG-часть (добавленная этой же сессией чуть раньше) устаревает и
   удаляется, памятка становится логин+пароль, как у iOS/desktop.
5. **Старый raw-`.fabackup` android device-type НЕ трогается** — по прямому
   решению пользователя остаётся временным запасным вариантом, снимается
   отдельным пунктом позже, когда автономный путь обкатается в бою.

## Жизненный цикл пира — постоянный, не ротируется

В отличие от iOS (пир живёт 8ч, каждая генерация убивает предыдущий), Android
получает **один постоянный WG-пир на первом логине**, дальше живёт, пока
аккаунт не удалят (решение пользователя, см. обсуждение). Практическое
следствие: приватный ключ должен быть **сохранён на портале**, а не только
единожды выдан и забыт (как у iOS) — иначе повторный `GET /api/v1/config`
(переустановка приложения, повторный вход с другого устройства и т.п.) не
сможет вернуть ТОТ ЖЕ пир, только новый — что тихо задвоило бы записи в
`wgcl.conf`/тратило бы IP-пул.

## Компоненты

### 1. Данные (`vkturn-ios-portal`, `User` struct, `main.go`)

Три новых поля, **отдельные** от iOS-шных `WGIP`/`WGPubkey` — разная
семантика (iOS: ротация, приватный ключ никогда не хранится; Android:
перманентность, приватный ключ обязан храниться) и разный жизненный цикл;
общие поля превратили бы редкий, но возможный случай "один логин — оба
устройства" в баг:

```go
AndroidWGIP      string `json:"android_wg_ip,omitempty"`
AndroidWGPubkey  string `json:"android_wg_pubkey,omitempty"`
AndroidWGPrivkey string `json:"android_wg_privkey,omitempty"` // хранится, в отличие от iOS
```

`nextFreeIP` (main.go:156) сейчас сканирует только `u.WGIP` по всем
пользователям — добавить сканирование `u.AndroidWGIP` туда же (один общий
пул адресов на интерфейсе `wgcl`, те же коллизии, что уже разрешает эта
функция для iOS).

### 2. Провижининг + самолечение (`ensureAndroidWGPeer`, новая функция)

Вызывается из `handleAPIConfig`'s ветки `device=android` при КАЖДОМ запросе:

- Если `u.AndroidWGPrivkey == ""` (первый раз): `nextFreeIP` → `wgGenKeypair`
  → записать все три поля → `saveUsers`.
- **Всегда**, независимо от того, только что создан пир или уже существовал:
  `wg set cfg.WGIface peer <AndroidWGPubkey> allowed-ips <AndroidWGIP>/32`
  (идемпотентно — безопасно звать много раз с теми же аргументами) + запись
  того же пира в `wgcl.conf` тем же приёмом, что `rewritePeerBlock`, но под
  ДРУГИМ маркером — `# ios-portal-android:<username>`, не
  `# ios-portal:<username>` — иначе один и тот же человек с обоими профилями
  (iOS + android-логин) затирал бы блок друг друга при regex-замене.

Это даёт самолечение бесплатно: если `wgcl.conf` когда-нибудь потеряет пир
(ручная правка, миграция интерфейса), следующий же `/api/v1/config` его
восстановит — identity (ключи, IP) при этом не меняется.

**Рефакторинг, нужный для разных маркеров:** `rewritePeerBlock` (main.go:229)
сейчас хардкодит `"# ios-portal:" + username` внутри себя — маркер не
параметр. Чтобы android-блок писался под своим тегом (см. компонент 2),
нужно вынести префикс маркера (`"ios-portal"` / `"ios-portal-android"`) в
параметр функции и поправить единственный существующий вызов из `swapPeer`
(main.go:216), чтобы он явно передавал `"ios-portal"`. Механический
рефакторинг, не меняет поведение iOS-пути.

### 3. Порт вычитания CIDR (JS → Go)

Без этого пункта фича не работает вообще — не второстепенная деталь.

`AllowedIPs` в WG-конфиге не может быть голым `0.0.0.0/0`: сокеты
Go-подпроцесса ядра (TURN-дайл, забор кредов с хаба) физически нельзя
`protect()`-нуть от собственного wg0-туннеля на телефоне (ядро — отдельный
subprocess, не gomobile-код в том же процессе, что мог бы дёрнуть
`VpnService.protect()`) — без исключения диапазонов VK-TURN туннель
зацикливается на себя и не работает. Ровно эта причина, по которой в
`make-backup.js`/`panel.js` есть `allowedIpsExcluding`/`cidrRange`/
`rangeToCidrs` (чистая битовая арифметика над IPv4, ~30 строк).

Портировать эти три функции в Go как есть (механический перевод, не
редизайн) + новое поле конфига портала `wg_exclude_cidrs []string` (те же
два диапазона VK, что уже в `panel-secrets.json`'s `wg.excludeCidrs`:
`95.163.0.0/16`, `90.156.0.0/16`).

### 4. Текст `.conf` и JSON-контракт

`.conf`, который строит портал (тот же формат, что и `panel.js` строит
сегодня руками):

```
[Interface]
PrivateKey = <AndroidWGPrivkey>
Address = <AndroidWGIP>/32
DNS = <cfg.DNSServers>

[Peer]
PublicKey = <cfg.WGServerPubkey>
AllowedIPs = <allowedIpsExcluding(cfg.WGExcludeCIDRs) + "::/0">
Endpoint = 127.0.0.1:9000
PersistentKeepalive = 25
```

`Endpoint = 127.0.0.1:9000` — не конфигурируемое значение, а соглашение
(локальный `-listen` ядра-подпроцесса на самом телефоне), как и в
`panel.js`/`make-backup.js` — хардкодится строкой, не тянется из конфига
портала.

`DesktopConfig` (api.go:61, тот же контракт, что уже расшаривают
desktop/android) получает одно новое поле:

```go
WgConfig string `json:"wgConfig,omitempty"` // omitempty - у desktop/ios остаётся пусто
```

### 5. Android — `PortalApiClient.kt` + `SettingsViewModel.kt`

`PortalConfig` (`PortalApiClient.kt:13`) — одно новое поле:
`val wgConfig: String`, парсится так же, как остальные (`json.optString`).

`SettingsViewModel.loginToPortal()` (`SettingsViewModel.kt:246`) — в уже
существующий вызов `ClientConfig(...)` добавляются два поля, использующие
уже существующие константы (`ClientConfig.wireGuardActive` и так проверяет
именно эту пару):

```kotlin
tunnelTransport = if (cfg.wgConfig.isNotBlank()) TunnelTransport.WIREGUARD else TunnelTransport.NONE,
wireGuardConfig = cfg.wgConfig,
```

Больше в Android НИЧЕГО не меняется — `WireGuardConfigCard` не трогается
(остаётся для ручного raw-import пути), никакого нового экрана/диалога не
появляется.

### 6. `panel.js` — откат WG-части `androidlogin`

`genAndroidLoginArtifact` (добавлена этой же сессией 2026-08-29, ДО этой
спеки) убирает вызов `buildAndroidWgPeer` и WG-блок из памятки —
`androidLoginMemo` перестаёт принимать `wgConf`, текст становится
логин+пароль+"войди в приложении, WireGuard настроится сам". Ссылка `🔑`
(peerSnip) в списке устройств пропадает для `androidlogin` — панель больше
не владеет этим пиром, портал теперь единственный источник истины.

### 7. Снятие аккаунта (`cliDelUser`)

Один блок, зеркальный уже существующему для iOS:

```go
if u.AndroidWGPubkey != "" {
    if err := removePeer(cfg, username, u.AndroidWGPubkey); err != nil {
        return fmt.Errorf("remove android wg peer: %w", err)
    }
}
```

## Не трогаем

- `genArtifact('android')` (raw `.fabackup`, весь WG+креды одним файлом) —
  по прямому решению пользователя остаётся временным запасным вариантом.
  Снимается отдельным решением позже, не частью этой работы.
- iOS-путь (`handleGenerate`/`WGIP`/`WGPubkey`/8-часовая ротация) — не
  меняется, отдельные поля гарантируют отсутствие пересечений.
- Desktop-путь — `wgConfig` у него всегда пустой (`omitempty`), клиент его
  не читает.

## Тестирование

Тот же метод, что уже применялся в этой сессии для `androidlogin` (живая
проверка на одноразовом тестовом аккаунте, не на семейных):

1. **Портал** (Go): создать тестового android-логина (`addandroid`), дважды
   дёрнуть `GET /api/v1/config?device=android` — второй раз должен вернуть
   ТЕ ЖЕ `AndroidWGIP`/pubkey/privkey (проверка идемпотентности), `wg show
   wgcl peers` должен показывать ровно один пир на тестового пользователя
   между вызовами (не задвоился). Снести тестовый пир вручную из `wgcl.conf`
   и повторить запрос — пир должен вернуться (самолечение). Убедиться, что
   `AllowedIPs` в ответе НЕ содержит диапазоны из `wg_exclude_cidrs`.
2. **panel.js**: создать/отредактировать `androidlogin`-профиль, убедиться,
   что памятка больше не содержит WG-блока и что `🔑`-ссылка пропала из
   списка устройств.
3. **Снятие**: `deluser` тестового аккаунта → пир пропадает из `wg show`.
4. **Android**: юнит-уровня тестов нет готовых под этот файл (`SettingsViewModel`);
   при появлении реального устройства для теста — живая проверка: войти по
   паролю тестового аккаунта, убедиться, что WireGuard поднимается без
   захода в `WireGuardConfigCard` вообще.

## Открытые вопросы для этапа реализации (не блокируют спеку)

- Точное имя нового конфиг-поля портала для exclude-листа
  (`wg_exclude_cidrs` — рабочее название, не обязано быть финальным).
- Нужна ли live-проверка на реальном Android-устройстве перед тем, как
  считать фичу закрытой, или достаточно проверки JSON-контракта — решить по
  ситуации (нет устройства под рукой в этой сессии).
